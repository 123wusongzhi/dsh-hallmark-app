## A 先看结论

```callout ok 已经对齐
DSH 承载两个应用：当前插件负责 Ozon 经营，未来采集箱负责来源资料。
现在先用统一接口连接旧采集箱，以后换成新的采集应用。
本次重点是工具流畅、数据准确；不另建“第六感”系统。
```

| 决定 | 已定方向 |
| --- | --- |
| 采集工具 | 搜索、读资料、读依据和素材，共三个能力 |
| 默认返回 | 一个够用的资料形态，内容按需展开 |
| 上品入口 | prepare 自动组合资料，不是审批 |
| 商品规格 | 支持多 SKU 同批、同 SKU 多件、跨 SKU 组合 |
| 包装规则 | 单组共用、重量叠加、尺寸复用；null 才问 |
| 用户界面 | 保留 ERP 表格、筛选、批量编辑与逐行状态 |
| 写入审核 | 所有经营写入走统一入口；规则能判断就直接处理 |

## B 架构图：入口不变，采集来源可以替换

```flow
旧采集箱 -> 旧平台适配器: 现在
未来采集应用 -> 规范商品资料: 以后 / 相同契约
旧平台适配器 -> 规范商品资料: 字段映射
规范商品资料 -> Agent 精简输出: 去重与分页
规范商品资料 -> ERP 表格: 展示与编辑
规范商品资料 -> 当前插件: 商品事实
当前插件 -> 上品准备: 店铺关联 / 规则 / 类目
Agent 精简输出 -> Agent: 三个采集能力
上品准备 -> Agent: 一次准备必要资料
Agent -> 统一审核执行: 制作并提交
统一审核执行 -> Ozon: 请求与结果跟踪
```

| 谁 | 保存什么 | 对外做什么 |
| --- | --- | --- |
| DSH | 会话与宿主运行上下文 | 提供应用入口、工具和可用图片能力 |
| 采集箱 | 原文、来源商品、SKU、报价、属性、原图 | 提供版本明确的规范资料 |
| 当前插件 | 采购关联、采用成本、包装覆盖、规则、草稿、回执 | 定价、上品、调价、库存、下架与促销 |
| Agent + skill | 制作过程依托程序保存 | 判断、写标题属性、制作图片、修改成品 |

这些是职责划分，不是要求新增多个服务进程。

MySQL 属于未来采集应用内部。当前插件不直接读它的数据库表。

图中的规范资料保留完整事实。Agent 和表格读取不同形态，但数据同源。

## C 三个采集能力：少量工具，够用的资料

| 能力（拟新增） | 使用场景 | 默认返回 |
| --- | --- | --- |
| collection.search | 找商品 | 每页 30 张卡片、总数、来源与类目计数 |
| collection.read | 读取已知商品 | 公共事实、SKU 表、主图、描述、未知与展开入口 |
| collection.resource.read | 看图或查依据 | 可查看图片、指定原文、目录或下一段 |

```tree
默认商品资料
  身份和版本 | 不靠标题、行号猜商品
  公共事实 | 属性、包装、单位、起订量、海关编码
  SKU 表 | 列名一次，只写差异；默认最多 40 行
  图片 | 主图地址与短编号；其他图片数量及入口
  来源描述 | 前 1500 字和续读入口
  unknowns | 来源缺失、冲突等真正未知
  available | 有资料，只是这次没有返回
```

关键词只匹配商品事实。“未上 bill”用店铺状态筛选，不匹配旧任务文字。

“已在哪些店”来自当前插件的经营记录。部分规格上架、已发任务、已上架分别显示。

包装数据只有一组时，按已定规则让所有 SKU 共用。

图片由程序下载缓存。返回的资源必须在 Agent 所在环境可查看。

```callout info 为什么能少读很多
已知噪音不进默认返回：重复表单、可选值字典、多语言重复和旧任务明细。
实际属性值与原始依据保留。Agent 可以追查，不依赖有损模型摘要。
```

| 用户提供的原型测算 | 旧返回 | 精简返回 |
| --- | --- | --- |
| 单商品处理后详情：中位数 | 30 KB | 2.0 KB |
| 单商品处理后详情：最大 | 137 KB | 9.6 KB |
| 搜索一页 | 100 条约 129 KB | 30 条约 8 KB |

这是原型字节统计，本轮未重跑。不是 token 测量，也不是上线承诺。
搜索页条数不同，不能直接据此算同等任务节省比例。
2 KB 不是上限；批量结果另有预算和继续读取入口。

## D 一句“这 10 个都上到 bill”如何执行

```sequence num
participants: 你, Agent, 当前插件, Ozon
你 -> Agent: 10 个已选商品 / SKU + 上品指令
Agent -> 当前插件: listing.prepare（拟新增）
当前插件 --> Agent: 资料、关联、规则、类目和包装结果
Agent -> 当前插件: resource.read（需要图片或原文时）
当前插件 --> Agent: 可查看资源
Agent -> Agent: 按 skill 制作并查看实际成品
Agent -> 当前插件: plan.create / revise
当前插件 --> Agent: 草稿、报价与具体缺项
Agent -> 当前插件: plan.submit
当前插件 -> 当前插件: 规则检查 / 必要的独立图文审核
当前插件 -> Ozon: 发送通过的行并跟踪回执
Ozon --> 当前插件: 处理中 / 字段错误 / 完成状态
Agent -> 当前插件: plan.get / inspect（按需）
当前插件 --> Agent: 逐行结果，不重发成功商品
Agent --> 你: 完成情况和仍需决定的问题
```

有选择就不再搜索。prepare 组合资料，不增加审批或重复 facts。

类目未定时返回候选，选定后再读该类目的必填字段。

可一次处理十个，也可按资料量分批。批量大小不固定为三个。
已读资料按版本复用，草稿和素材交程序保存。

对话历史不会因为分批而自动消失。精简输出减少新增负担，不承诺清空模型记忆。

| 现有经营能力 | 在流程中的用途 |
| --- | --- |
| hallmark.pricing.read | 读取店铺规则 |
| hallmark.pricing.quote | 有需要才额外试算 |
| hallmark.plan.create / revise | 保存成品或修改对应行 |
| hallmark.plan.submit | 统一审核与提交 |
| hallmark.plan.get / inspect | 查看草稿或核查原请求 |

## E SKU、包装与利润：程序直接处理

```flow LR
来源共用值 -> 包装规则
SKU 专属值 -> 包装规则
用户维护表 -> 包装规则: 优先覆盖
销售组成与数量 -> 包装规则
包装规则 -> 草稿与定价: 有值，继续
包装规则 -> Agent 询问: null，问具体缺项
```

| 规则 | 程序如何做 |
| --- | --- |
| 商品只有一组包装 | 默认全部 SKU 共用 |
| 单 SKU | 用户维护 → SKU 来源 → 商品共用 → null |
| 多件或多 SKU | 成员重量 × 数量后相加 |
| 组合尺寸 | 用户维护或组合已有值优先，否则复用成员已有完整尺寸 |
| 多组尺寸可选 | 默认按保存的组成顺序取第一组，可在表格覆盖 |
| 规则无结果 | 按字段返回 null；不填零，不清空其他有效值 |

不要求重新测量，不新增包装审核，不让 Agent 再判断规则是否合理。

用户维护表展示：商品/SKU、组成数量、长宽高、重量、取值方式和缺项。
人工覆盖不被同步抹掉。清除覆盖后恢复自动规则。

下方可以改数量、填写覆盖值或移除来源重量，查看规则如何返回结果。
所有操作仅影响演示，不保存到真实应用。

| 动态物流规则 | 已定值 |
| --- | --- |
| 售价低于 135 元 | 固定费 3.16 元 |
| 售价达到 135 元 | 固定费 18 元 |
| 两方案共同部分 | 39.3 元/kg，佣金 20% |
| 多方案条件重合 | 取当前售价与重量下总费用最高的方案 |
| 上品 / 日常调价目标 | 60% / 5%，用于建议售价 |
| 最低利润与售价限制 | 独立可选设置，未设置就不额外加底线 |

真实售价变化后重新匹配方案；动态计算会反映利润变化，并不保证任何折扣都不亏损。
已有商品优先使用已取得的实际物流重量。历史记录不随新数据改写。

## F 审核与异常：只在关键位置处理

| 事情 | 谁负责 | Agent 要做什么 |
| --- | --- | --- |
| 身份、采购组成、成本、公式、范围、重复请求 | 程序 | 使用结果，解决明确缺项 |
| 包装共用、叠加、尺寸复用 | 程序规则 | 有值继续；null 才问 |
| 标题、图片、件数和属性含义 | 独立决策模型 | 根据具体意见修改实际成品 |
| 决策模型不可用 | Host 的独立模型子代理 | 无需主 Agent 自己宣布通过 |
| Ozon 字段拒绝 | 平台 + 错误翻译 | 看哪个字段、原因、怎么改 |
| 限流、处理中、未知写入结果 | 后台执行程序 | 按原请求查看，不换身份重发 |
| 关键事实或经营意图无法确定 | 用户 | Agent 只问具体问题 |

决策模型沿用 OpenRouter 的 openai/gpt-6-luna-decisions。
服务端读取环境变量 openrouter；工具、页面和 Agent 上下文不返回密钥。

机械检查能补全就自动补全；Ozon 自己校验的内容不在本地再建一套。
没有“我看过了”的声明、双录 facts、强制重复回读或固定等待 60 秒。

同一内容问题首次退回后，允许两次实际修改尝试，再决定是否升级。
技术等待不消耗修改次数。修改共享内容时，程序识别受影响的销售行。

```callout info 三种状态要分开
已发送、已导入、已上架不是同一件事。
程序和 Agent 只汇报已经取得依据的状态。
```

## G 哪些已经有，哪些这次做，哪些以后做

| 阶段 | 内容 | 对旧平台的关系 |
| --- | --- | --- |
| 已有基础 | 独立店铺凭据、Ozon 请求、经营规则、动态利润、草稿及审核执行 | 部分准备过程仍读旧采购详情 |
| 本次目标 | 三个采集能力、精简资料、资源访问、prepare、多 SKU 包装维护 | 采集仍来自旧平台，但经营调用不再散落依赖旧接口 |
| 本次迁出 | 历史采购关联、旧费率参考、旧回执与经营启动依赖 | 在当前插件保存，日常经营逐步独立 |
| 以后完成 | DSH 独立采集应用、MySQL、采集管理界面与数据素材搬迁 | 最终替换旧采集提供者 |

旧原始读取入口留作显式追查。新 Agent 默认用新能力。
旧表格需要的结构由兼容层保留，结构变更同时升级契约和调用方。

采集资料暂留旧平台期间，还不能宣称彻底关闭旧平台。
同一数据源搬家保留商品、SKU、素材身份与历史关联。

## H 执行次序与验收：怎样算真正做完

```timeline v
01 | 固定资料与接口 | 统一身份、字段含义、默认返回与继续读取方式
02 | 接入旧采集箱 | 来源映射、搜索去噪、SKU 分页、图片直接查看
03 | 接入经营准备 | prepare 组合店铺、类目、包装和规则
04 | 做维护表与多 SKU | 单 SKU、组合 SKU、人工覆盖与 null 分支
05 | 接通原经营流程 | 草稿、审核、执行、部分失败与旧调用迁移
06 | 验证并安装 | 按真实调用检查资料、成品、回执与 DSH 使用
```

| 验收情景 | 应看到的结果 |
| --- | --- |
| 阿里来源字段多 | 关键属性、包装、单位可读；编辑器噪音不默认返回 |
| 淘宝有 335 个 SKU | 分页不漏行，SKU 与图片精确关联 |
| 一组包装、多个颜色 | 自动共用，不要求额外声明 |
| 红杯两只或红蓝组合 | 重量叠加、尺寸复用；人工覆盖生效 |
| 规则算不出重量 | 返回 null，只问该项，其余商品继续 |
| 十个商品部分失败 | 修失败行，成功行不重发 |
| 切换采集提供者 | Agent 用法不变，历史商品关系不丢 |

阿里与淘宝先按样本验证；1688、拼多多样本不足，需补映射测试。
DSH 资源路径、具体调用接线、缓存和返回预算由实现核实。
这些是工程验证项，不要求你再选择一套业务方案。

当前交付是蓝图总览和可操作演示。生产接口、维护表、数据迁移及部署仍待实施。
