**推荐方案：把组件变成普通 React 源码工程。** Agent 直接编辑、安装依赖、构建和预览；查看真实截图后继续修改。现有组件仍可使用，新组件不再受 7 种 widget 和 4 种布局限制。

源码模板方案已实施，插件与服务 0.3.0 已安装并重开 DSH，440 项测试通过。实际验证与安装状态见 [0.3.0 交付记录](release-0.3.0.md)，使用方法见 [源码组件作者指南](source-component-authoring.md)。下文保留当时批准的设计方案。

## A 先明确实施原则

| 原则 | 实际做法 |
| --- | --- |
| 先给原始能力 | 直接写 TSX、CSS、JS 和资源文件 |
| 复用成熟设计 | 复制并修改真实 shadcn 页面、商品卡和图表源码 |
| 通过效果迭代 | 构建后截图，Agent 看图、操作控件，再改代码 |
| 具体问题具体修 | 依赖冲突处理冲突；卡顿处理性能；溢出处理布局 |
| 规范指导设计 | 配色、层级、留白、密度作为设计要求，不变成组件白名单 |
| 保留用户工作 | 草稿自动落盘，发布版本可回退 |

不预设组件种类、字段名、图表点数或 CSS 属性白名单。不另造模板语言，不用一套庞大接口替代 Agent 已有的文件和命令工具。

视觉规范继续沿用此前确定的标准。灰度可以帮助检查层级，交付效果应有完整配色。

## B 技术结构怎样接到现有项目

```flow
Agent 原有文件与命令工具 -> React 源码工程: 编辑和安装依赖
React 源码工程 -> Vite 构建: 生成同一份 dist
Vite 构建 -> 独立预览: 截图与交互验证
Vite 构建 -> DSH 组件面板: iframe 加载真实产物
独立预览 -> Agent 原有文件与命令工具: 图片与错误反馈
DSH 组件面板 -> 现有 Hallmark 服务: 数据与原生附件桥接
```

首版沿用 React 18、TanStack Table 和 Recharts，便于复用当前代码。补齐真实 shadcn/Tailwind 工程，再引入选定设计。

源码组件在 iframe 内独立运行自己的 React 和 CSS。宿主 React 18 不作为源码工程永久版本上限；需要升级时，按实际依赖验证。

旧 ViewSpec 渲染器保留在原路径。新源码组件增加独立展示入口，逐步替换旧模板。

## C Agent 实际获得哪些能力

建议工程放在 `E:/project/deepseek_h/dsh-hallmark-app/component-workspace/`。

```tree
component-workspace/
  collected-products/
    component.json | 名称、入口和模板来源
    package.json | 普通 npm 依赖
    package-lock.json | 可复现依赖版本
    src/
      Component.tsx | 完整组件源码
      styles.css | 自由编写样式
      components/ui/ | 复制的 shadcn 源码
      assets/ | 图片和本地资源
    .preview/ | 截图与交互结果
    dist/ | 实际发布页面
```

`component.json` 只记录工程信息，不定义页面布局。循环、条件、状态、事件、图片、图标、动画都由普通 React 实现。

Agent 使用已有文件和命令工具完成大部分工作。建议只增加一个打开入口：`hallmark_open_source_component({ directory })`。该工具登记构建产物、绑定当前聊天，并打开组件面板。

保存和更新沿用现有组件管理语义，扩展为可保存源码版本。接口负责接入 DSH，设计能力来自源码本身。

## D 视觉验证器怎样帮助 Agent 修改

```sequence
Agent -> 工程: 编辑 TSX 和 CSS
工程 -> 预览器: 构建并运行实际 dist
预览器 --> Agent: 截图、控制台错误、交互结果
Agent -> Agent: 查看截图，对照设计规范
Agent -> 工程: 修改具体问题
工程 -> 预览器: 再次构建与截图
预览器 --> 用户: 可操作的实际组件
```

预览器使用 Playwright 打开真实构建页面。输出截图路径、buildId、实际窗口尺寸和运行错误。Agent 用图像工具查看图片，不把“没有报错”当作“已经好看”。

先核验用户真正要用的状态：窄侧栏、宽标签页、搜索、勾选和附件按钮。需要空状态、深色或加载状态时，再补相应预览。

视觉验证器提供反馈，不给设计打一道僵硬的通过分数。Agent 根据层级、配色、留白、图片和信息密度判断如何修改。

**关键要求：预览和 DSH 加载同一份 dist。** 不再用简化 HTML 代替真实 React 界面验收。

[Playwright 截图文档](https://playwright.dev/docs/screenshots)

## E 数据与商品选择怎样接入

数据可来自 Agent 的查询结果、数据文件或现有 Hallmark 服务。组件通过普通 JavaScript 完成筛选、排序、聚合和派生计算，不必把每种计算预先写进渲染器协议。

提供一个薄的 TypeScript 辅助库，方便读取数据、刷新和附加选择。它用于复用现有能力，不定义可用的页面样式。

| 场景 | 处理方式 |
| --- | --- |
| 展示最近采集商品 | 读取真实列表，直接传给 React 表格或商品卡 |
| 显示利润率 | 展示真实源字段或明确的计算结果，并注明口径 |
| 计算汇总 | 在源码中实现聚合，显示本次数据范围 |
| 商品选择 | 将选择 keys 交给外层，从当前数据中取稳定商品 ID |
| 附加聊天 | 复用本次安装的原生 JSON 附件能力 |

有源值时不因字段名命中“profit”就静默隐藏。真正缺失的数据显示缺失；参考利润与实际结算利润用明确名称区分。

iframe 和外层使用消息桥接。外层已经知道当前聊天和组件，沿用现有服务连接。组件不需要处理服务密钥。

当前 `buildProductSelection` 依赖 ViewSpec 的 table/product_card。实施时抽出稳定 ID 与附件构造逻辑，让新旧组件共同使用。

## F 在 DSH 内怎样运行和保存

DSH 首版采用 iframe 展示完整页面。这使上游 CSS、Tailwind、弹窗和 React 根能按原设计运行，也让独立预览容易复现实际效果。

已核实宿主路由只接受精确路径。发布时枚举 dist 文件，为入口和资源逐项注册路径。Vite 使用相对资源路径，Host 返回正确的文件类型。

| 阶段 | 保存什么 |
| --- | --- |
| 编辑草稿 | 源文件自动落盘，避免服务退出丢失工作 |
| 预览 | dist、buildId、截图和运行结果 |
| 保存到组件库 | 源码、资源、依赖锁文件、数据配置和版本 |
| 再次编辑 | 从已保存版本生成工作副本 |
| 更新原组件 | 创建新版本，保留前一个可用版本 |

草稿自动落盘不等于自动发布到组件库。用户要求保存时才增加正式保存版本。

第一次接入要验证宿主 iframe、资源加载、宽窄布局和附件消息。该验证针对真实接入问题，不预先增加新的设计白名单。

[Vite 构建 API](https://vite.dev/guide/api-javascript.html) · [Vite 后端集成](https://vite.dev/guide/backend-integration.html)

## G 最小实施顺序与验收

| 阶段 | 交付内容 | 怎样判断完成 |
| --- | --- | --- |
| 1：源码和视觉迭代 | 一个有颜色的商品列表工程、预览脚本 | Agent 能改源码、看到截图、再改出明显不同的效果 |
| 2：接入 DSH | 同一份 dist 内嵌、数据桥、原生选择附件 | 用户在右侧勾选产品，输入区出现附件并能手动发送 |
| 3：保存复用 | 源码版本、缩略图、打开编辑和回退 | 服务重启后仍能打开；Agent 可基于保存模板继续设计 |

第一版选“最近采集商品”贯穿整条链：缩略图、商品名称、来源、可读时间、搜索和选择。窄栏采用图文列表，宽页采用可勾选表格。

先完成这一份真实模板，再扩展利润看板、商品卡和经营分析。无需先搭建完整低代码平台。

[shadcn 的 Vite 接入方式](https://ui.shadcn.com/docs/installation/vite)

## H 遇到问题时，再决定怎样处理

| 实际问题 | 优先修法 |
| --- | --- |
| 新依赖与当前 React 冲突 | 调整该依赖或工程版本，不禁止所有新依赖 |
| 大量商品导致卡顿 | 加分页或虚拟滚动，不静默丢弃超出数量的数据 |
| 窄侧栏内容溢出 | 修改该模板布局和响应式样式 |
| 图表口径不清 | 修改标签和计算说明，不按字段名一律隐藏 |
| 保存后更新失败 | 保留上个版本，返回具体错误供 Agent 修改 |
| 服务退出丢失临时组件 | 草稿落盘，重新打开工程恢复 |

每次新增规则都应能回答：出现了什么问题，有什么证据，为什么这个局部修复足够。没有实际问题时，不预先增加模板表达限制。

本方案继续采用此前确认的视觉规范。目标是让 Agent 具备完整前端制作与迭代能力，让组件库积累经过实际使用的源码设计。
