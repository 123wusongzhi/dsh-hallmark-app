# 采集箱与店铺销售状态

本次补充采集商品与 Ozon 店铺的状态关联。范围包括程序同步、Agent 查询、上品准备资料和原采集表格；不执行归档、恢复、改价或重新上品。

## 使用时的变化

采集商品保留两类信息：

| 信息 | 含义 |
| --- | --- |
| 采购关联 | 哪个店铺的销售商品对应这份采集资料，以及已确定的来源 SKU、组合数量和采购成本。归档不删除这些关系。 |
| 当前销售状态 | 在售、无库存、审核／处理中、已归档、发布失败、暂不可售或状态待确认。 |

一个采集商品可以同时显示「在售 4 · 已归档 2」。数量按去重后的销售商品 Offer 计算；多 SKU 组合不会因为引用多个采购 SKU 而重复计数。

原有 `status=listed/partial` 只表达历史成功铺货的来源 SKU 覆盖度，不能据此判定当前在售。Agent 判断当前状态使用 `saleStates` 和 `freshness`。

## 程序处理顺序

1. 搜索采集箱或准备上品时，程序检查目标店铺状态缓存；默认有效期 5 分钟。
2. 需要刷新时，完整读取 Ozon 普通目录及归档目录，分别分页，再按商品 ID 去重。只查状态所需商品详情，不同时重复读取价格或全部属性。
3. 以店铺、Offer 和 Ozon 商品 ID 对应已有记录，更新平台状态，保留采购关联、成本和历史成功信息。
4. 按采集商品聚合数量，再执行筛选、统计和分页。Agent 直接拿到结果，不需要自行查每个 SKU 或提交验证声明。
5. 已确认的归档操作、导入结果和精确详情回读立即更新对应记录；不必等待下一次整店刷新。

任一分页失败时，不把局部目录当成完整结果。旧关联保留，当前状态标为待确认／待刷新。完整目录找不到某个旧商品时，也只标记状态未知，不删除关联或猜成从未上架。

没有可靠采购关联的历史商品不会靠标题自动匹配。因此部分采集商品会显示「关联待确认」；这和「没有在售商品」不是同一结论。

## Agent 入口

`hallmark.collection.search` 的 `store` 支持组合条件：

```json
{"store":{"id":"目标店铺ID","saleState":"archived","association":"linked"},"limit":30}
```

`saleState` 用于当前销售状态，`association` 用于采购关联，旧 `status` 用于历史铺货覆盖度。`refresh:true` 主动重新同步。筛选先于分页和统计执行。

`hallmark.listing.prepare` 保留所有状态的既有商品关联，包括归档、失败和未知。关联多时随准备资料续页，不要求 Agent 另开大量查询；是否恢复旧商品或创建新商品仍由具体经营意图决定，不自动重发。

本轮只调用商品读取接口，没有向 Ozon 提交经营写入。旧采集接口和新精简接口都核对了真实返回数据。
