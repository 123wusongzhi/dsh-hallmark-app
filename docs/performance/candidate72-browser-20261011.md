# 列表格式化器复用：浏览器补验与延迟定位

日期：2026-10-11。结论：**接受列表格式化器复用，作为第五项优化合入本地分支**。实测收益显著，普通业务和同序事件的功能契约保持；逐次点击的小幅时间波动与自然坏图时序差异在下文明确披露，不声称所有可见状态绝对一致。基线为已合入四项优化的 `d5a41f3b216532768180a533975e4a87f4bdc169`，候选只增加列表格式化器复用。原先暂停的原因和两次负面记录仍保留在[首轮报告](candidate72-windows-selective-20261011.md)。

## 185 ms 尖峰实际发生在哪里

冻结原先的 React 测试渲染器 bundle，保留 500 件商品、30 个预热周期、100 个测量周期、每周期 11 个动作及每动作四次 `setImmediate` 等待。先运行 8 个追踪进程及 8 个无插桩对照，再用只向原有返回对象增加起止时间的轻量插桩运行 12 个进程。

轻量追踪在候选进程 `micro-trace-r2-s2-candidate` 的同一个 `round=70` 再现 **185.134 ms** 的清空选择耗时：

| 同一动作窗口，主线程区间取并集 | 耗时 |
|---|---:|
| 垃圾回收 | 183.658 ms，99.20% |
| 其中一次 MajorGC | 173.354 ms |
| 其中后续弱句柄清理回调 | 10.024 ms |
| 未被 GC 覆盖的其余时间 | 1.476 ms |
| 已记录的主线程编译/去优化区间 | 0 ms |

这次 MajorGC 的原生日志中，标记阶段约 160.2 ms，其中 ephemeron 弱引用关系标记约 111.6 ms；这些是嵌套阶段，不能再相加。对象堆从约 299.06 MiB 降至 35.45 MiB。追踪时间以同一主线程的单调时钟对齐，并在全部测量和卸载结束之后用一次 GC 校准；测量之前和之中没有强制 GC。

原测量把动作之后四次异步等待也计入“清空选择”。因此，这次记录主要是等待窗口内执行的大型 GC，并不代表清空选择的业务处理本身执行了 185 ms。原来的 212.980/198.862 ms 没有追踪，无法倒推那两次的精确内部拆分；现在有的是同一工作负载、同一轮次的同类尖峰及明确 GC 证据，不把推断冒充旧事件的直接记录。

进一步检查发现，旧控件查找会遍历 ReactTestRenderer 后代，创建并通过 WeakMap 关联大量 TestInstance 包装对象。新增独立诊断只将两处查找换为读取已提交的 Fiber host props，保留事件、数据、等待、计时边界和完整输出。三个进程的输出及每个进程的 1,100 个动作序列全部保持一致；两个候选进程的 MajorGC 最大暂停分别 **1.713/1.661 ms**，测量窗口内各次匹配的 MajorGC 日志中 ephemeron 标记在日志精度下均记为 0.0 ms，清空选择最大值 **3.111/3.235 ms**。基线仍保留一次其他动作 102.432 ms 的负面结果。

这个对照支持旧控件查找及测试包装对象路径放大 GC 的解释；它同时改变了查找成本和 GC 调度，不能证明 WeakMap 是唯一原因。也不能据此认定 Intl 析构是原因：弱句柄回调只占 10.024 ms，且没有对象类型信息。私有 Fiber 读取只用于诊断，不进入产品。没有证据支持给产品的清空处理添加延迟、强制 GC 或 V8 参数补丁。

## 真实 Chrome 的正式结果

Windows、Chrome `154.0.8037.95`、Node `v24.12.0`，现有依赖保持不变。使用实际组件的生产构建、真实 React DOM、CSS、iframe 数据桥和浏览器布局，Chrome 为 headless 模式。输入是合成商品及本地 data URL 图片，不连接真实 Ozon、模型或正在运行的 DSH。

48/500 件表示载入的数据量，每页仍显示 20 件。每个独立 Chrome 进程预热 30 周期，再测 100 周期；每周期包括搜索、来源筛选、翻页、单选、本页选择及清空等 11 个动作。全部串行 A/B/B/A，不与构建、测试或其他性能任务并行。共 **48 个正式进程**，没有剔除离群值。

| 场景 | 每版进程 | 每周期同步处理和布局中位数：基线 → 候选 | 减少 | 测量调用区间的主线程任务时间减少 |
|---|---:|---:|---:|---:|
| 48 件，桌面 | 4 | 47.925 → 30.950 ms | 35.42% | 35.05% |
| 48 件，手机布局 | 4 | 38.000 → 21.100 ms | 44.47% | 44.61% |
| 500 件，桌面 | 10 | 58.825 → 39.650 ms | 32.60% | 31.86% |
| 500 件，手机布局 | 6 | 45.750 → 25.575 ms | 44.10% | 43.02% |

中位数是各进程中位数的中位数；每组 ABBA 的周期耗时和主线程任务时间均改善。主线程任务时间来自 CDP `TaskDuration`，其区间还包含快照、校验及结果序列化，不等于纯渲染 CPU，更不是整个应用的加速比例。

| 清空选择 | 每版次数 | p95：基线 → 候选 | 最大值：基线 → 候选 |
|---|---:|---:|---:|
| 48 件，桌面 | 400 | 7.0 → 4.4 ms | 15.0 → 7.4 ms |
| 48 件，手机布局 | 400 | 5.7 → 2.0 ms | 9.4 → 2.8 ms |
| 500 件，桌面 | 1,000 | 6.6 → 4.7 ms | 32.3 → 8.1 ms |
| 500 件，手机布局 | 600 | 4.4 → 2.1 ms | 14.3 → 3.0 ms |

每版共 2,400 次清空选择，均没有超过 50 ms 或 100 ms 的动作。全部 26,400 个候选动作最大 13.0 ms；基线有一次其他动作 53.6 ms。浏览器仍记录到了批次级长任务：例如 500 件桌面候选有 108 条、最大 97 ms，基线 1,000 条、最大 149 ms。不能把“单个清空动作无长尾”改写成“浏览器没有长任务”。这里 11 个动作连续运行，周期末才等待两次 rAF，长任务还包括组合操作及测量框架工作。

另外两个独立 Chrome 进程保留了含 V8 GC、主线程任务和 CPU 采样的完整 trace。候选已解析的 GC 区间中没有达到 20 ms 的事件；清空选择标记最大 7.749 ms，基线 15.466 ms。基线另有 24.259 ms 的增量标记启动区间。追踪有额外开销，这些只作诊断，不混入上表正式计时，也不证明候选没有 GC。

以上单动作字段包含原生 DOM 事件分派、`flushSync`、React 提交及强制布局。双 rAF 是绘制机会，不能证明物理屏幕已经呈现，也不是 INP。另行使用可信的真实逐次点击作补充验收，见下节。

## 逐次点击与功能检查

500 件商品分别在桌面和手机布局进行一轮 ABBA，共 8 个独立进程。每进程 30 个预热、100 个正式周期，每周期“选择本页→清空选择”，使用 Playwright 可信 `locator.click`，不使用 `flushSync`；每次点击后等待双 rAF，再检查两个响应式分支的 20/0 选择数量、页复选框、页脚和附加按钮状态。全部检查及初始/预热后/最终完整快照对照通过。

| 真实逐次点击，每场景每版 200 次清空 | 桌面：基线 → 候选 | 手机布局：基线 → 候选 |
|---|---:|---:|
| click 事件到第二次 rAF 中位数 | 15.3 → 15.3 ms | 15.4 → 15.6 ms |
| 同上 p95 | 15.9 → 15.8 ms | 16.0 → 16.1 ms |
| 同上最大值 | 20.8 → 19.1 ms | 19.1 → 16.7 ms |
| 100 周期调用区间的主线程任务时间 | 3169.54 → 2577.74 ms | 2481.00 → 2016.95 ms |

两种布局的主线程任务时间分别减少 18.67%/18.70%，区间包括页面内验收工作、正常 CSS 和自动滚动。**负向结果不删除：** 手机布局清空和本页勾选的绘制机会中位数均增加约 0.2 ms，p95 均增加约 0.1 ms。双 rAF 受帧调度影响，未据此宣称可见响应普遍更快；清空的最大值均下降，所有 1,600 个正式可信点击均无超过 50 ms 的绘制机会耗时。这个补验每版每布局只有两个进程，不提供统计置信度或 INP 保证。

当前工作分支重新执行的 97 项回归、主项目和组件类型检查、组件生产构建、Apps/Host 打包及 1 项实际安装包 Runtime 隔离测试全部通过。两个生产文件的 SHA256 与浏览器测量候选一致。

独立功能检查覆盖四种规模/布局的完整查询顺序、所有分页、大小写及空格搜索、来源筛选、空结果、跨页选择、价格日期文本及属性。v4 的完整普通帧、查询结果、相同起点和同序错误事件下的图片处理、初始及最终状态均一致；v3 正式计时各进程的初始、预热后、最终帧也一致。

**保留一个可见边界差异：** 将图片来源换为立即失败的 data PNG 并触发隐藏分支解码时，基线会在一个响应式分支留下坏图节点，候选在两个分支都显示占位图。v3 四组基线均是桌面分支保留坏图；v4 中 500 件桌面这组变为移动分支保留，其余三组仍为桌面。自然观察均被保存，总体 parity 仍标记 `needs-review`，没有伪装成完全一致。

这个结果没有出现候选新增的功能缺失，表现朝已有占位提示方向改善，但不能承诺所有图片加载时序逐像素一致，也不能把它宣布为已修复图片竞态。图片组件、错误处理、懒加载属性及表格 cell 身份均未修改。`useEffect` 重置失败状态与原生 error 事件竞争是待验证解释；受控错误处理相同不能推翻自然时序差异。

## 合入范围与复现

生产改动只有 `Component.tsx` 和 `lib/products.ts`：每次组件调用创建一组惰性的日期及币种格式化器，同一次渲染内复用；不跨渲染缓存，不缓存商品数据或格式化字符串。原有 helper 导出、日期及货币选项、缺值/非法值回退、刷新、选择和接口均保留。

日期和价格的兼容测试覆盖 208 个价格组合、三个时区、缺值/非法值、构造次数、同键数据刷新、选择保留及跨渲染时区变化。对于会暂时失败后恢复的自定义 Intl/polyfill，同轮缓存失败可能减少重试；本项目采用原生 Intl，没有声称这类人为替换也完全等价。
