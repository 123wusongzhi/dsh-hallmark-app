## 合入的四项

下表是对应测试工作负载的耗时中位数，不能相加或解释为整个应用的加速比例。

| 优化 | 测量范围 | 基线 → 候选 | 耗时减少 | 决定 |
|---|---|---:|---:|---|
| 采集商品上架状态的请求内索引 | 367 个商品、600 个 offer、60 个计划，每计划 15 行，2 个店铺；真实 Runtime 查询 | 46.174 → 34.950 ms | 24.31% | 合入，5/5 轮改善 |
| 分块数据解码直接写入字节数组 | 约 333 KB，初次读取、内容不变、内容变化的三次读取 | 35.710 → 6.886 ms | 80.72% | 合入，5/5 轮改善 |
| 同上 | 约 2 MB 的同样三次读取 | 223.277 → 43.326 ms | 80.60% | 合入，5/5 轮改善 |
| 大字符串分页避免完整字符数组 | 1.72 MB ASCII，127 页完整读取 | 2577.066 → 1561.644 ms | 39.40% | 合入，5/5 轮改善 |
| 同上 | 1.72 MB 混合文本，127 页 | 3771.084 → 3377.986 ms | 10.42% | 合入，5/5 轮改善 |

大字符串的进程 CPU 分别减少 35.94%、9.25%、10.04%，进程峰值 RSS 分别减少 36.53%、47.46%、32.73%。这不是已部署应用整体内存的测量。经营编辑持续运行的 CPU 中位数从 734.5 降到 633.0 ms，减少 13.82%；4/5 轮改善，另一轮增加 2.23%。

索引只在当前请求内使用，不跨请求缓存。直接字节复制保留原有校验和缓存流程。分页仍以原来的字符位置、预算和错误规则工作。JSON 仍在组件第一次初始化时生成，保留后续编辑状态。

## 负面结果与权衡

保留全部测量，没有删除异常值或只挑选最快的一轮：

- 8 商品的小查询从 2.548 降至 2.464 ms，收益很小，其中一轮慢 2.56%；不声称所有小请求都会加速。
- 未走分块解码的 inline 对照从 0.1371 到 0.1385 ms，差约 0.0014 ms；该路径没有改动，不归功于优化。
- 432 字节的小字符串完整读取从 4.797 到 4.926 ms，增加约 0.129 ms（2.69%）；不同轮次方向不一。
- 43 KB 文本耗时减少 2.08%，但进程 CPU 中位数从 32.0 到 46.5 ms。Windows 的短任务 CPU 分辨率较粗，而且这里测量的是首次完整读取，不据此声称小文本 CPU 有收益。大文本的耗时、CPU 和内存改善稳定且明显，综合接受这项改动。
- 经营编辑原短测耗时减少 21.56%，但包含预热的 CPU 从 141.0 到 164.5 ms，增加 16.67%，4/5 轮出现增加。另做固定预热、预热后才开始计 CPU 的持续运行补验，得到上表结果。两组测量覆盖不同区间，补验不抹去原短测的负面结果；轻量场景与持续操作的耗时均改善，综合接受。

## 暂不合入：列表格式化器复用

这项优化的功能输出一致，收益也很大：48/500 商品的短测周期耗时减少 58.09%/59.98%；500 商品持续交互减少 64.28%，CPU 减少 54.78%，均为 5/5 轮改善。

但体验风险没有通过筛选。原短测的单选 p95 从 5.013 增到 12.251 ms；持续测试单选 p95 回落至 1.934 ms（基线 5.480 ms），却在两个不同候选进程的相同测量轮次（从零计数的 `round=70`）观察到“清空选择”耗时 212.98 和 198.86 ms。这发生在 30 个预热周期之后，不能未经追踪便解释成首次暖机或垃圾回收。

| 清空选择，双方各 1000 次 | 基线 | 候选 |
|---|---:|---:|
| 中位数 | 2.869 ms | 0.791 ms |
| 均值 | 3.446 ms | 1.638 ms |
| p95 | 3.629 ms | 4.358 ms |
| 最大值 | 85.039 ms | 212.980 ms |
| 超过 16.67 ms | 5 次 | 5 次 |
| 超过 100 ms | 0 次 | 2 次 |

这些是无浏览器渲染的测试耗时，阈值不是丢帧证明。多数操作更快，但极端延迟有重复证据；在没有进一步解释和真实浏览器验证前，不把它当作体验保持的改动合入。候选实现、原始输出及两项格式化兼容测试保留在本地验证目录。

## 功能有变化但值得关注的两项

以下仅报告，没有合入，也没有据此声称模型成功率、费用或整条业务链路速度改善：

1. **工具说明按预算精简。** 对本地真实注册的 91 个工具进行确定性渲染，总模型侧输出从 238,424 降到 168,116 字节，减少 29.49%；超预算而不可用的说明从 1 个降为 0 个（`apps.authoring.inspect`）。这会改变 Agent 看到的说明内容，需要单独验证信息是否足够。
2. **大结果增加字面短语定位。** 在 75,468 字节的合成说明中恢复已知短语所在完整段落，答案包括例外条件且两版一致；命中时从 6 次工具调用/77,972 字节降到 3 次/23,964 字节。未命中时从 6 次/77,972 字节降到 1 次/529 字节。这增加读取接口能力，适合单独评估后再合入。

归档中的按行 ID 读取、超大结果返回、调用恢复、刷新/继续执行、采购默认设置、会话权限和 CLI 重试等也可能改变接口或业务行为，本次没有混入这四项实现。

## 验证方法与边界

环境：Windows `10.0.26200`，Intel Core i5-14600KF，Node `v24.12.0`，使用已有的相同依赖，无安装或升级。全部正式计时串行运行，不与测试、构建或另一个基准并行。

共 320 个独立计时进程：后端 100、原前端 80、字符串读取 100、持续交互补验 40。每个场景做 5 轮 A/B/B/A，每版 10 个独立进程。后端每进程预热 5 次、测 15 次；前端原始业务场景预热 3 个周期、测 15 个周期，其 CPU 窗口包含预热；持续补验业务预热 30、测 200，列表预热 30、测 100，CPU 从预热之后开始。

读取基准是每个新进程在 Host 初始化之后的首次完整读取，包含 HTTP、JSON、哈希和断言开销，没有读取链路预热。前端通过真实组件的 React 测试渲染器驱动交互，不包含浏览器布局和绘制。所有业务输入均为合成数据，没有调用真实 Ozon 业务、模型或付费接口，也未安装到正在运行的 DSH。

正确性证据：

- 后端对完整响应、模型侧投影、来源调用、事件、SQL/参数和数据库行进行逐项比对。小/中场景分别覆盖 473/12,389 条 SQL 记录，输出完全一致；覆盖重复记录、异常记录、后续请求修改、刷新失败和两次状态读取间的外部 SQLite 提交。
- 分块读取覆盖初次/不变/变化数据、Unicode、调用者修改返回值、7 类篡改失败与重叠读取，14 条两版记录一致。
- 字符串读取完成 1,749 次差分比较，其中 258 次错误响应；4 类文本完整重建一致，覆盖代理对、孤立代理字符、预算、偏移和错误行为。
- 经营编辑 0/20 属性场景的完整渲染帧与请求一致，每场景 43 个帧；持续测试初始、预热后和最终帧一致。图片失败后的既有表现保持，未混入归档的图片状态修复。
- 五项试验候选已通过 97 项回归、主项目/列表组件类型检查、组件构建、Apps/Host 打包，以及 1 项实际安装包隔离测试。最终四项在当前工作分支重新执行检查：93 项回归全部通过，主项目及组件类型检查、组件构建、Apps/Host 打包和 1 项实际安装包隔离测试全部通过；四个生产文件的 SHA256 与计时候选一致。
