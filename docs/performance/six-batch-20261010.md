# Candidate55 six-patch integration validation

Scope: GitHub issues #4, #5, #6, #7 revision 2, #8 and #11, based on `0d2d4c1e801d35b6ea62581ad4259ffd518c4533`. This branch does not contain withdrawn #9, conditional #10, #7 appendices, Collator caching or prepared-statement experiments.

The production changes are: stable ordered OR indexes for composition joins; avoid writing an identical fresh source archive while repairing missing/divergent archives; skip an unrelated snapshot read only when provenance is self-contained; filter scheduler provider records in SQLite while preserving accepted JSON/error semantics; evaluate the procurement whole-row global search once per row; lazily reuse bounded native number formatters. No data/schema migration, deployment or live business call is performed.

## Reproduction environment

- Node 24.19.0, pnpm 11.25.0, SQLite 3.53.3, ICU 78.3, React/test-renderer 18.3.1.
- Two isolated complete checkouts: clean baseline and complete combined source. Both root installs use `pnpm install --frozen-lockfile --ignore-scripts`; both component workspaces use `npm ci --ignore-scripts` against their checked-in package locks.
- Configure writable `PNPM_HOME`, `--store-dir` and `npm_config_cache` where the cloud default home does not exist. No lockfile changes are needed.
- Generate SDK, build Apps and plugin artifacts separately in **each** checkout before testing. Never restore baseline source over candidate-generated bundles.
- The existing receipt-template test reads `../audit-inputs/A2-30f8a9809dd4/dsh_apps_A2/templates`. Populate its two input files byte-identically from the baseline's tracked `docs/requirements/A2/templates/{build-receipt,preview-receipt}.schema.json`; do not regenerate schemas from implementation.
- The existing date test expects the calendar date in `2026-10-08T00:00:00Z`. Matched prepared tests use `TZ=Asia/Shanghai`; the native cloud timezone is America/Los_Angeles and its original date-test failure is retained in initial logs. The patch changes no date formatting.
- Run `bash scripts/performance/six-batch/checks.sh /absolute/evidence-dir` in each root. Functional tests use `--test-concurrency=1` to avoid existing renderer fixtures' fixed-delay races.
- Twelve existing browser-gated tests need a working `DSH_PREVIEW_BROWSER_PATH`; skips are not passes. This cloud's installed Chromium cannot create its required singleton socket (`Operation not permitted`) with a fresh profile, including the permitted launch retry. No browser-security flags were changed.

The 20 added tests cover composition join ordering/deduplication, fresh-cache archive repair and restart, provenance fallback, scheduler scope/accepted JSON/error precedence, bounded formatter behavior, and coupled procurement search/formatting semantics. Additional differential harnesses compare the complete actual client trees/callbacks and real Runtime/SQLite responses.

The same three existing Linux failures occur in both arms, all `rmdir` returning `ENOTDIR` on symlink-related fixture cleanup:

1. `symlinks in Runtime, external workspaces and backup input are rejected instead of followed`

3. `resolver rejects anchor tamper, mapped file tamper, symlink, traversal, unmanifested mappings and conflicting proven facts`

This is **zero new matched failures**, not a claim that every repository test or browser check passed. The initial default-timezone/concurrent runs and their additional prerequisite/race failures are retained separately; they were not overwritten by the prepared run.

## Combined performance evidence

### Production React client, complete combined source

100 fresh processes: five ABBA cycles for each of five shapes, 10 processes per arm per shape. Each process performs 15 same-mounted six-action cycles, excluding the first three warm-up cycles. Each cycle searches for a miss, searches for an offer, searches all rows, clears, sorts price and edits display. The metric below is the sum of that cycle's six measured action durations, summarized as the median of process medians. It excludes checkpoint serialization between actions and is not browser paint/FPS or live-network latency.

| Loaded / visible rows | Baseline ms | Combined ms | Reduction |
|---|---:|---:|---:|
| 10 / 10 | 36.752 | 16.343 | 55.53% |
| 76 / 10 | 49.188 | 21.759 | 55.76% |
| 267 / 10 | 61.010 | 25.281 | 58.56% |
| 1000 / 10 | 92.117 | 32.008 | 65.25% |
| 267 / 20 | 98.982 | 39.059 | 60.54% |

Every action's median improved in these five measured shapes. All 25 paired ABBA cycles improved the six-action workload (minimum cycle reduction 47.3%); median cold mounts also improved in all five shapes. All 100 processes retained equal first/last-cycle host-tree hashes, exactly one snapshot request and zero Apps events; request bodies matched after normalizing only the generated scope identity. Separate differential correctness runs compare complete values, not just hashes: 53 ProductList scenarios, 1,159 formatter/error/mutable-data cases, and nine complete Workbench frames. Peak process RSS was lower in each shape; full CPU/RSS and p95 statistics are in `six-batch-client-summary.json`. These are diagnostic fixture results, not a universal speed guarantee.

### Runtime / SQLite backend

60 fresh processes, five ABBA cycles for each of three shapes. Every sample directly times one complete Runtime.invoke plus a due scheduler.tick → presentation.refreshBinding → second Runtime.invoke in the same real disk SQLite database. Two warm-up turns precede eight measured turns per process. The realistic-size synthetic cases have 267 products/postings, 1,000 unrelated legacy snapshot rows and 100 unrelated cache records; the small control has one product and no unrelated rows. No historical per-issue measurements are added together.

| Backend shape | Baseline ms | Combined ms | Median reduction | ABBA direction |
|---|---:|---:|---:|---|
| 267 product rows | 221.201 | 107.909 | 51.22% | 5/5 improved, 48.9–53.8% |
| 267 posting rows | 228.741 | 121.938 | 46.69% | 5/5 improved, 46.0–48.8% |
| 1 product, no noise | 8.502 | 7.636 | 10.19% | 4/5 improved; first cycle 4.00% slower |

The small control's first paired cycle was 7.939 → 8.256 ms (+0.318 ms), so this experiment does not establish an invariant small-case speedup or zero timing variance. Small-control median peak RSS increased from 102.43 to 103.32 MiB; product/posting cases fell from 262.88/270.03 to 178.23/178.61 MiB. Backend CPU totals for the eight warm turns and assertions were lower in all three shape medians; full process/cycle values are in `six-batch-backend-summary.json`.

All 60 timing processes passed output-content digest and per-arm source-hash checks, with 20 actual Provider calls, 10 scheduler refreshes and zero upstream I/O per process. Separate deterministic functional runs compare all complete response fields and schedule state plus 25 database tables, allowing only the fresh archive physical timestamp difference described below. Both product/posting repair, missing archive, failed upstream refresh, stale fallback and real restart checks passed; after the refresh-failure path, all 25 tables match exactly between arms.

## Overall conclusion and publication boundary

The complete six-patch stack shows repeatable net improvement in the two measured representative backend workflows and all five measured production-renderer client workflows, with no new matched repository failure or observed API/UI semantic regression. This is not an all-green repository/browser certification, a browser paint measurement, a live-platform load test, a claim that every input is faster, or a sum of six independent improvement percentages. The three historical Linux test failures, twelve browser checks not run, small-control variation and intentional archive physical metadata change remain explicit.

Independent backend and client reviews found no new scope-specific blocker. Publication is a separate approval gate. The experiment itself does not commit, push, open a pull request, merge, deploy, install the bundle into DSH, or contact a real shop.
 The reusable backend and production React client harnesses are in `scripts/performance/six-batch/`. Their fixtures are synthetic; they do not contact a store, submit native chat text, modify real snapshots, or use credentials.


## Archive metadata contract

Avoiding a redundant fresh-hit write intentionally leaves the durable archive row's physical `updated_at` unchanged. That changes raw SQL forensic exports and logical/physical backup fingerprints relative to the old needless-write behavior. It does not promise byte-identical databases. The source payload, `fetchedAt`, expiry/cooldown decisions, complete API responses, plan state and row ordering remain equal in the checked fixtures. Missing/divergent archive repair, upstream-failure fallback and real restart are separately exercised.

The actual maintenance GC dry-run, rollback baseline and rollback assessment match between arms. Each arm's real backup → verify → restore preserves all original rows/metadata across 25 tables; only expected evidence-relocation records are added. Backup fingerprints differ as expected, and each backup verifies against its own fingerprint.
