# 工作台联动取消后的自动刷新恢复

日期：2026-10-16  
修复提交：`ec76ad6f2008ae983199cbe05f75969ce8e67b21`

## 用户可见问题

在商品浏览组件中，用户选中商品，SKU 读取尚未结束时，提交商品搜索或读取下一批。列表读取成功后会取消原 SKU 请求并清除选择，但遗留的 SKU 忙碌标记会阻止后续自动刷新。界面已回到“请选择一个商品”，实际上却仍认为有读取在进行。

此时点击“立即更新”，即使读取成功，也不会清除这个标记。因此，用户可能看到快照自动更新的提示，但更新计时器已经停止。重新选择商品并等待读取完成，或切走再返回，可以恢复，不能作为正常使用的必要步骤。

两次均复现：搜索成功、原 SKU 请求已取消、选择已清除，但 SKU 忙碌标记仍为真，自动刷新计时器为零；随后手动更新成功，计时器仍为零。

探针运行真实 `WorkbenchInstanceView`、`ProductList` 和 `SkuDetail`，网络替换为封闭的本地只读响应，不访问商家平台。

## 原因与最小修复

源码位置：[工作台组件](../packages/plugin-apps/client/workbench-board.tsx)。

- 列表搜索或翻批成功后，`clearLinkedSelection` 清除联动选择、取消请求并删除暂停读取记录。
- 被取消请求的 `finally` 有意不再更新状态，避免旧响应污染新的请求。
- 原清理过程没有删除对应联动绑定的 `pending` 标记。
- 自动刷新看到任意绑定仍忙碌，就不再安排计时器。

生产代码只增加两行：一行说明和一行定向清理，将本次明确取消的联动目标从 `pending` 中移除。其余绑定的忙碌状态不变。原有取消信号、请求代际和身份保护全部保留，未放宽旧请求 `finally` 的执行条件。

不改变后端、平台业务写入、导航或缓存策略。

## 回归验证

新增正式测试：[联动取消回归](../test/plugin-apps/workbench-linked-cancellation.test.ts)。

四个场景为搜索／翻批与不服从取消信号的迟到成功／失败响应的组合。每个场景覆盖：

1. 取消 SKU 读取后恢复自动刷新。
2. 旧响应返回前快速重新选择，旧成功或失败均不能清除新请求的忙碌标记。
3. 取消后隐藏并重新显示，不恢复已经取消的读取，不重复请求。
4. 自动刷新只发起一次读取，手动刷新后仍可继续自动更新。
5. 卸载时移除计时器。

正式测试使用录制商品数据作为基础，显式控制身份别名、延迟、错误和计时器，并登记于数据测试范围清单。
