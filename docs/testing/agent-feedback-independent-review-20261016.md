## 结论与修补

候选正确区分 native queue 接受与业务完成：`accepted` 仅表示已提交并排队；`prepared`、`dispatching`、`unknown`、`failed` 不宣称业务完成。更新与提交阶段都有明确等待文字，双击仍只产生一个请求，未知回执不解锁重试。

独立挂载生产 React 组件、以受控 Promise 探针复现两个基线既有问题，候选同样存在：

1. 已成功发布上下文后，再次更新失败，旧 published/revision 仍使请求按钮可用。修补在失败时使旧发布状态失效，要求显式重新更新；文字说明失败发生在上下文更新阶段。
2. 同一已挂载控件更换 bridge 身份，继承旧任务输入、提交锁及晚到回执。修补以 protocol/session/view/build/frame 的稳定值为内层组件 key，让新身份独立初始化，旧异步响应不能污染新实例。普通 props/hello 对象重建不改变 key，不解除未知提交锁。

另补充候选恢复指引的边界：传入检查回调但错误没有 request ID 时，无法显示检查按钮；现在仍显示回到当前聊天核对的指引。这个补丁不生成请求 ID，也不允许盲重试。

## 错误上下文建议

值得保留的用户上下文是失败阶段、原 request ID（有则用于核对）、是否确定尚未提交以及下一步。现有错误 message 配合本次阶段提示足够支撑此小范围 UX；暂不需要新聊天或任务系统。后续如需展示错误码，宜提供可展开的诊断信息，而非把内部堆栈或请求参数直接暴露给用户。

跨真正卸载的未知任务持久化仍不在此补丁范围；稳定身份隔离不宣称可以恢复已卸载组件的回执历史。
