# 调价范围、确认与恢复体验验证（2026-10-16）

## 范围和原问题

基线：`fd95bc22929bfbfa850e0312357322578287a10c`。测试执行生产 `BusinessOperations` React 组件、生产业务引擎和内存 SQLite，通过替换 `fetch` 的封闭 fixture 端点连接两者。商品标题、店铺名称来自仓库已校验的公开脱敏冻结快照；货号别名、售价、币种组合、选择状态、回执与故障均是明确的测试控制，不是新的真实商家记录。

复现操作：选中 3 行（CNY / RUB / CNY），筛选后只显示 OFFER-A，批量填入 25 并保存。旧组件以整批已选行计算批量填写范围，实际修改全部 3 行，包含已隐藏的 2 行。第二组独立场景只选择并显示 OFFER-A，旧“提交整批变更”按钮会立即向业务引擎提交全批 3 行。旧界面已有整批文字提示，但没有解除筛选的全范围确认。

## 修改

- 批量填价只作用于当前可见、已勾选、可编辑的价格动作。隐藏选择数量持续显示，可以查看隐藏选择或清空勾选。
- 每次仅填写一个明确币种；混币先选择币种，旁边说明其他币种或缺币种有多少行不修改。缺币种行无法批量填写，不进行换算。零价不能批量填入。
- 改价保存仍只调用 `revise`，不提交。保存后再显示新的报价；未保存时保留“上次保存报价 · 修改后待重算”标记。
- 预计利润与利润率直接显示，费用详细项仍保留。没有增加自行计算或猜测利润的逻辑。
- “确认整批范围后提交”先打开全批确认区，列出所有货号、动作、改前与提交值（含币种）、状态、已有预计利润，以及隐藏/未勾选数量。确认区打开时禁用修改，返回检查不会提交。
- 确认提交仍传递原有 `planId` / `expectedRevision`，不把勾选当作后台提交范围，不修改审核、规则、并发、幂等或未知结果处理语义。
- 提交等待有明确提示；结果按状态计数。未知回执显示检查入口，业务未知结果仍显示“结果待核查”，不会被描述成全部成功。
- 无匹配结果时，一次“清除筛选”重置搜索与状态，不丢失草稿。

## 实际前后指标

| 场景 | 基线 | 修改后 |
|---|---|---|
| 3 行已选、只显示 1 行，填价保存 | 修改 3 行，其中隐藏 2 行 | 修改可见 1 行，隐藏 2 行原值保留 |
| 同时勾选 CNY / RUB | 一个值可写入全部币种 | 先选币种；CNY 2 行改动、RUB 1 行不改，旁边解释 |
| 只显示/勾选 1 行，整批提交 3 行 | 1 次点击直接提交 | 2 次点击，最后一次之前展示全部 3 行与两类遗漏数量 |
| 查看已保存利润与利润率 | 每行需打开费用明细 | 0 次展开，直接可见，仍标记陈旧报价 |
| 同时有搜索和状态过滤导致空结果 | 分别重置两个控件 | 1 次清除筛选 |

增加一次提交确认是明确的安全成本，本次不宣称总点击数普遍下降，也不以主观美观作为结论。

## 执行命令

安装已有依赖后，普通回归使用当前生产代码：

```sh
node --test test/plugin-apps/business-price-journey.test.ts
```

历史复现显式从 Git 读取固定基线的 UI 文件，只替换该次临时编译输入，不回写源码，不切换业务数据：

```sh
DSH_PRICE_JOURNEY_BASELINE=1 node --test test/plugin-apps/business-price-journey.test.ts
```

该历史模式要求本地 Git 对象中包含固定基线提交。普通 CI 不启用此模式。

## 已验证与边界

- Node 24.21.0 和 Node 22.18.0 的上述相关回归各 130/130 通过；数据来源审计和类型检查通过。
- 保存、打开确认和取消确认均 0 次 fixture transport 写入。
- 同一事件轮连续确认两次，仅 1 个提交请求。
- 失去回执后只读恢复，不重发；恢复计划保留 succeeded / rejected / unknown 三种状态。平台核查只检查 unknown 行。
- 修改并保存失败行后再次明确确认，仅该行新增 1 次 fixture 写，另外两行不重发。
- 已知的提交前 409 错误保留草稿；再次打开后取消没有新增提交。
- 生产业务引擎、价格计算、适配器及公开冻结数据未修改。本次没有连接商家，没有真实平台写入，没有修改或安装桌面包。
- React 组件执行和业务引擎 fixture 验证不等于浏览器实际交互、视觉、原生宿主或真实业务验收；这些范围仍未签认。
