## 一、任务目标与事实边界

目标有两个，分别验收：

1. **运行可靠性**：Agent 创建的组件在 DSH 中能完成实际数据读取和展示；遇到暂时断连或 Runtime 重启时，能够安全、有限地恢复。
2. **完成判定准确**：系统和 Agent 明确区分“构建通过”“发布已接受”“实际展示成功”，不把旧构建或旧文档的成功当成本次成功。

历史那次“Runtime 暂不可用”不能证明 Runtime 进程退出。此前已确认并修复的是同步扫描约 49 MB 业务记录等问题；本次另行加固完整展示链路。

## 三、尚未完成：必须优先处理的项目

### 1. 文件完整性缓存修复【P1，阻止发布】

**审查复现：** 展示通过验证后修改归档文件，数据库身份不变，旧缓存仍允许读取，最长持续 10 分钟；清除缓存后才报 `BUILD_EVIDENCE_INVALID`。

**已进行：** W4 正把缓存命中改为每次检查文件成员、stat、ctime、realpath、符号链接及回执身份；只对未变化文件复用哈希，不再靠 TTL 延迟检测。

**尚缺：** 修改完成后的类型检查、TTL 内篡改/同尺寸恢复 mtime/新增删除文件/符号链接替换回归，以及独立审查者重跑原始复现。不能把“已经开始修改”记为修复完成。

### 2. 三项展示完成契约边界【P2，阻止最终验收】

W1 修复中被停止，三项均尚未取得独立复核通过：

| 缺陷 | 应达到的行为 |
|---|---|
| 同一 display 换发新 frame/nonce 后，旧 ready 仍让 outcome 显示成功 | 新文档必须有自己的 ready；旧成功只作为历史证据 |
| 旧 `failed_mount` / `interrupted` 遮蔽正在重开的展示，等待立即结束 | 合法的新 opening 展示进入等待；真正取消或被替代仍拒绝 |
| legacy `startMount → authorizeFrame → renderReadyV1` 已成功，却一直报告待展示 | 将真实 legacy ready 归一化成精确身份的证据，不把所有 mounted 一概当成功 |

## 五、后续建议顺序

### 第一步：恢复现场，先确认现状

1. 保留当前工作区；不 reset、stash 或覆盖原有修改。
2. 检查被停止子代理留下的半完成编辑、新增文件与测试；先跑类型检查，不能假设文件处于最终一致状态。
3. 检查此次测试自建进程、端口与锁是否有残留，仅处理能证明属于此次测试的资源。停止子代理后没有另行完成全部 OS 子进程清理核验，不能承诺无残留，更不能终止未知 Runtime。

### 第二步：按优先级完成现有修复，不再扩展功能

1. W4 文件完整性窗口。
2. W1 三项 ready/恢复/兼容状态缺陷。
3. 独立复核 W6 历史发布身份及 scheduler、慢分块修复。
4. 定位重启证据拒绝，并完成 W2 同发布自动重开。
5. 让原审查者逐项重跑最初的 5 个复现，不用实现者自报代替复核。

### 第三步：统一冻结后验收

1. 生成 SDK，核对编号调用和描述；补齐新测试分类。
2. 类型检查和全量测试；要求失败逐项清零或明确列为阻塞，不删除关键断言。

- 没有把所有业务计算迁入 worker_threads；当前主要通过索引、异步编排、验证复用减少阻塞，不能说请求线程已无同步工作。

- `runtime-child.log` 尚无轮转；异常存活 child/保守遗留启动锁可能需要人工核查，系统不会自动强杀。
- 无可信启动清单的现有安装不会自动获得重启能力。
- 没有保证“以后永不加载失败”；应交付的是有限恢复、明确失败原因和准确完成判定。
