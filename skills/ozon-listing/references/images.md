# 图片代理：选参考图、生图、交付

先读 [共同前提](shared.md) 和 [进度与恢复](image-progress.md)。你从商品图片中选取参考主体，生成每个销售行的商品图和详情图，并交付公网地址。

## 输入

- production.json：销售行（saleId、规格、包含物）、product.json 的路径和版本。
- product.json 中的 `images[]`：资料代理已经筛选好的来源图。
  - `subject`：主体参考图；
  - `specification`：尺寸图、参数表；
  - `detail`：细节图。

开工前运行 `node <本 skill 目录>/scripts/handoff.mjs check <product.json>`。不通过就报告主 Agent。

## 交付数量

每个 saleId 交付两组图：
- **images**：7 张。第 1 张是首图，必须用图上文案说明本行规格，例如"5 контактов · 10 шт."。
- **richContentImages**：8 张详情图。讲什么、按什么顺序，由你按商品自行决定。

除首图外，其余图片只要内容适用，就可以跨 saleId 复用。复用时不重复生成，也不在同一组里重复排列同一张图。

## 整套图的参考分配

生成前先查看 product.json 中的可用来源图，按每张成图的目的分配参考图，尽量利用已有的不同角度、结构和细节资源。

- 有多张适用来源图时，优先组合使用多张互补参考图，不默认每次只传一张。
- 同一 saleId 的 7 张商品图和 8 张详情图，优先选用不同的适用主体图，并按主题搭配细节图、尺寸图等，让各张图的参考图或参考组合尽量不同，不整套固定使用同一张。
- 参考图的相关性和主体一致性优先。素材不足或同一张图确实最适用时允许复用，不为求不同而使用主体不符、模糊或无关的图片；每次仍须附上适用的主体参考图。

## 每张图的步骤

1. **定目的**：用一句话说清这张图要让买家理解什么。
2. **选参考图**：
   - 从 product.json 的 `images[]` 中选 1 张或多张 `subject` 图作为主体参考，这一步每张图都必须做；
   - 要表达结构、细节或用途时，搭配对应的 `detail` 图；
   - 要表达尺寸或参数时，再加上对应的 `specification` 图；
   - 一张图里有多个主体时，在提示词里写明用哪一个，例如"左侧绿色端子"。
3. **写提示词**：按下面的骨架写，控制在三四句话内。
4. **登记并生成**：
   - 按 image-progress.md 登记 `generating`，references 填第 2 步选的图；
   - 调用 `listing_image_prepare({progressPath, assetKey})`；
   - 把返回的 prompt 原样传给 `codex_image_generate`，`referenceImages` 附上第 2 步选的来源图。
5. **看图**：打开成图，对照参考图，只检查主体的形状、构造和颜色是否一致。不一致时，用同样的参考图重新生成。
6. **交付**：归档并登记 staged，发布后登记 published。

## 提示词

骨架：

> 为参考图中的〈主体〉制作〈首图／商品图／详情图〉，表达〈目的〉。整体风格：〈风格〉。文案：〈文字；不需要文字就省略这一项〉。以参考图中的〈主体〉为准，保持形状和构造不变。

说明：
- 骨架里的占位说明要换成实际内容，不传给生图模型。
- 构图、字体、光影、背景交给生图模型，提示词里不写。

例子（规格和文案只是示意，实际以 product.json 为准）：

- **首图具体案例：4位主体参考，销售2P～12P**。以下模板已用同一原始参考图，全新生成一轮11张首图，主体审核11/11通过。这是不同销售 SKU 的首图验证，同一 SKU 的整套图仍按上面的参考分配原则选图。
  > 为参考图中的4位绿色插拔式 PCB 接线端子制作简洁工业风商品首图。画面直接使用参考图的4位原商品，不重绘、不增减结构；销售规格只通过文案说明。文案："Клеммник 3,81 мм" "{销售规格} · 1 шт." "На фото — образец серии на 4 контакта; в комплекте коннектор на {销售规格}"。

  本案例只替换 `{销售规格}`，例如 `2 контакта`、`12 контактов`。“4位”是参考照片中的主体规格，不随销售SKU改变；换商品或参考图时，按真实主体更新描述及系列示例说明，不沿用本案例的4位数值。
- **不放文字的场景图**：
  > 为参考图中的盘架制作厨房收纳场景图，表达餐盘整齐、取用方便。风格温馨自然，画面无文字。保持盘架的形状和构造不变。
- **尺寸详情图**：同时附上主体图和尺寸图。
  > 为参考图中的盘架制作尺寸详情图，让买家直观理解大小。风格清晰简洁。文案："Размеры""Ширина 150 мм · Глубина 120 мм · Высота 80 мм"。保持盘架的形状和构造不变。

图上文案用俄语，由你根据事实构思，不用等文案代理。风格按商品来选；颜色变体可以用不同色调区分，但不强制。

## 尺寸

- **商品图**：900×1200，3:4。用生图工具的尺寸参数指定；工具没有尺寸参数时，才写进提示词末尾。
- **详情图**：按平台当前富文本图片要求选择。先读应用提供的约束，没有提供再查 Ozon 官方说明。可以和主图同画幅，也可以不同。
- **画幅不对**：用生图能力重新调整画幅，不硬拉伸。

## 发布

调用 `hallmark.listing.assets.publish({files:[{path:"/abs/xxx.png"}]})`，每次最多 20 个文件。返回里失败的文件（包括 `LISTING_ASSET_TIME_BUDGET`）用原文件再调一次；已经成功的文件会直接复用。只有返回成功的 url 才能写进交付。

## images.json 结构

```json
{
  "factsRevision": 1, "salesRevision": "…", "preparationRevision": "…",
  "rows": [{
    "saleId": "sale-a",
    "status": "complete",
    "images": [{"role":"main","path":"/abs/a-main.png","url":"https://…","references":["img-1"]},
               {"role":"additional","path":"…","url":"…","references":["img-2"]}],
    "richContentImages": [{"role":"detail","path":"…","url":"…","references":["img-3","img-4"]}],
    "referenceSubjects": [{"sourceImageUrl":"https://来源图地址","subject":"左侧绿色端子"}],
    "issues": []
  }]
}
```

字段说明：
- `images` 正好 7 项（首项是 main），`richContentImages` 正好 8 项。任何一项没有 url，整行标 `incomplete`，并在 issues 写明原因。
- `referenceSubjects` 只在来源图有多个主体时填写，用来说明比对的是哪个主体。
- 不生成 11254 的 JSON，主 Agent 和程序负责组装。

## 红线

- 参考图只用 product.json 中的来源图，不用任何已生成的图。每次生图都要附上主体图，不能只附参数表或规格图。
- 不改造主体（扩孔、增减部件、换颜色）去凑规格；规格差异用首图文案说明。
- 提示词原样使用 listing_image_prepare 返回的内容，不在调用时追加背景、灯光、构图描述。
- 图上文字由生图模型生成，不用脚本叠字；没有生图能力时如实报告。
- 只写 images/、images.json 和 image-progress.json。
