# Ozon 上品

默认完成标题、属性、主图和详情的制作，查看最终成品后提交。用户已有的上品授权持续有效；仅在关键商品事实无法确定、需要改变销售规格或经营目标时提问。

## 工作入口

通过当前会话的 Apps 网关发现 Hallmark 已启用连接和能力版本。已选商品直接调用 `hallmark.listing.prepare`，传入店铺与 `selections:[{id,skuIds?}]`，不重新搜索这些商品。多 SKU 组合通过 `compositions:[{id,members:[{itemId,sourceSkuId,quantity}]}]` 明确组成；单 SKU 默认逐个销售。制作后使用 `hallmark.plan.create / revise / get / list / submit / inspect / restore`；`hallmark.listing.draft.*` 是同一经营草稿的别名。以实际 `apps_describe` 返回的字段和版本为准。

读取、比较商品、尝试文案和保存草稿不调用决策审核。`submit` 把确定版本送入统一审核，程序选择规则或模型并执行通过的内容。无需另写审核声明、证据清单、preflight 或“我看过”的证明。

店铺连接与经营规则由应用自己的「经营设置」维护。通过 `hallmark.pricing.read` 读取规则，通过 `hallmark.pricing.quote` 以真实商品/采购引用试算；不要让用户重复输入已经保存的物流报价。Ozon 请求和回执由新经营应用负责，采集资料仍从原平台读取。

## 制作成品

- `prepare` 一次给出精简商品事实、SKU、包装计算、采购报价、已有店铺关联和类目候选或模板。已有资料用 `knownRevisions` 复用。日常选品用 `hallmark.collection.search`，单独读资料用 `hallmark.collection.read`；不默认读取完整原始 JSON。
- 用 `hallmark.collection.resource.read` 按返回的短编号查看图片，需要具体依据才按路径展开原始资料。批量资料、SKU、描述分别按返回的续页输入继续读取，不自行写下载命令或反复尝试读取被截断的结果。
- 使用 DSH 宿主的图片能力制作或编辑图片，实际查看输出。生成文件通过 `hallmark.listing.assets.publish` 一次交付为 Ozon 可读取的公网地址；传本机绝对路径及对应 SKU 即可，程序处理导入、缓存和字节核对，无需旧平台的工作计划、素材声明或手写上传脚本。
- 一个商品仅有一组包装数据时默认共用；单 SKU 人工值覆盖来源，组合重量按数量叠加、尺寸复用已有值。应用在草稿中填入克/毫米与自动售价。用户在「经营设置 → SKU 尺寸与重量」维护。包装返回 null 时只补具体缺项，不加包装审核或声明。
- 明确每个销售 SKU 对应的来源 `itemId`、`sourceSkuId` 和组成 `quantity`。采购价格、币种、单位和合计由程序从来源读取计算，不从商品名称猜对应关系、不把自填采购金额当来源。
- 根据当前类目和字典填写 Ozon 原生字段，内容只写一份。无需再维护一套同内容的 facts。不同颜色、容量或套装的主图、件数与标题保持对应；可共享的详情复用同一内容。
- 按需阅读 [图文制作方法](references/content.md)，完成标题、属性、主图和详情。制作方法服务于商品本身，不强制每个商品沿用固定标题或版式。
- 将实际 Ozon 字段放入 `payload`，将采购引用放入 `procurement`。保存后查看程序计算的采购绑定、成本和具体问题，修正当前需要处理的部分。
- 来源图有多个主体时，在行级 `referenceSubjects:[{sourceImageUrl:"实际来源图片地址",subject:"左侧银色贴片"}]` 标出当前 SKU 要比较的对象；单一明确主体可省略。这是素材定位，不是审核声明，不放进 Ozon `payload`。固定图片题由程序维护：主图印出的规格文字是否符合 SKU、有字时是否清晰、成图与指定来源主体是否相符。无规格字或无文字分别记为不适用；不数细密方格，也不从短样图外形推断精确尺寸或整卷长度。低信心由独立模型继续判断。
- 纯文本详情写入 `payload.attributes` 的 `4191`（`values:[{value:"正文"}]`），富文本详情使用 `11254`。正文只写一份；若使用 `payload.description`，程序会自动转为 `4191`。两者同时存在时保留已有非空 `4191`，空 `4191` 才由 `description` 补齐；保存、审核和提交使用转换后的同一份内容。
- 自动定价时设置 `pricing: {mode: "automatic"}`；明确指定售价时用 `mode: "manual"`。应用的动态物流规则会按实际待提交售价和重量自动匹配方案，多个方案匹配时取费用最高者，不需要 Agent 指定渠道；只有旧固定方案模式才使用 `planId`。程序依据采购组成、包装重量和规则计算并填入建议价，跨价格区间时重新匹配。读取返回的 `pricingQuote` 即可，不自己重算一遍或把目标利润误当硬性底线。缺少规则、重量或来源事实时只解决该缺项。
- 查看最终实际图文；在用户已授权的目标和范围内调用 `submit`。由 Host 启动独立审核；决策服务不可用时使用独立大模型子代理，主 Agent 不手工模拟审核通过。

## 处理返回结果

- 精确使用返回的 `planId`、版本和稳定 `rowId` 修改对应行。已成功行不重新提交；共享内容改变时由程序确定需要重新审核的行。
- 平台返回字段问题时，读取字段、原因和建议，必要时再查询对应类目属性选项，修改后继续提交。平台规则不在本地自行重建一份。
- `pending` 表示平台仍在处理；`unknown` 表示原写入结果未明。调用 `get / inspect` 查看原请求，不新建同一动作或更换请求标识绕过状态。等待和轮询交给程序。
- 明确拒绝且可修正的继续修改；来源资料互相矛盾或修正会改变经营目标时，向用户说明具体需要决定的事实。
- 展示真实结果：草稿、已发送、平台处理中、退回、已导入与已完成各有区别。平台确认导入不自动等于买家可购买。

## 常见草稿形状

下面只是结构示例，示例标识不可拿去操作真实店铺。`payload` 使用当前 Ozon 类目要求的真实字段：

```json
{
  "storeId": "已确认的店铺ID",
  "title": "本批上品",
  "rows": [{
    "action": "listing",
    "target": { "offerId": "已确定的销售货号" },
    "pricing": { "mode": "automatic" },
    "procurement": [{ "itemId": "来源商品ID", "sourceSkuId": "来源SKU", "quantity": 2 }],
    "payload": { "name": "制作完成的商品标题", "images": ["已发布的实际主图地址"] }
  }]
}
```

接口本身负责身份一致性、必要上下限、重复写入和异步执行。Agent 将精力放在商品判断和具体修改上。
